# Splunk Alert Investigation and Triage

## Overview

This document describes the investigation workflow used to review a Splunk alert for potentially suspicious PowerShell activity in a Windows lab environment.

**Environment:** Windows 10 VM, Sysmon, Splunk Universal Forwarder, and Splunk Enterprise on Kali Linux.

## 1. Alert Identification

The detection search identifies events containing `powershell.exe` and `whoami`.

When the scheduled search returns matching events, Splunk generates an alert according to the configured trigger condition.

**Initial classification:** Suspicious activity requiring investigation.

An alert alone does not confirm a security incident.

## 2. Initial Triage

The analyst should establish:

- **What happened?** Identify the command and associated process activity.
- **Where did it happen?** Identify the affected Windows host.
- **Who executed it?** Identify the account associated with the event, if available.
- **When did it happen?** Record the event timestamp.
- **Why might it matter?** Determine whether the command was expected or could indicate reconnaissance.

## 3. Evidence Collection

Review the matching event in Splunk and record the available evidence.

| Evidence | What to examine |
|---|---|
| Timestamp | When the activity occurred |
| Host | Windows machine that generated the event |
| User | Account associated with the process, if available |
| Process image | Whether PowerShell was executed |
| Command line | Commands and arguments executed |
| Parent process | Process that launched PowerShell |
| Related events | Other activity immediately before and after execution |

Not every field will necessarily be present in the original event. Collect additional telemetry where available.

## 4. Investigation Steps

### Step 1: Review the alert

Open the triggered alert and inspect the matching event. Confirm that the event contains the expected search terms.

### Step 2: Examine the process activity

Review the available process command line, parent process, user, and host information. Determine whether the activity fits the user's normal work or the lab test.

### Step 3: Correlate surrounding events

Search for related process creation events and other relevant Windows telemetry around the alert timestamp.

Look for unexpected command interpreters, unusual parent processes, repeated discovery commands, or suspicious network activity.

### Step 4: Assess the evidence

Consider whether the activity was authorized, whether other suspicious events support the alert, and whether the evidence is sufficient to justify escalation.

### Step 5: Document the outcome

Record the evidence reviewed, the analyst's reasoning, and the final disposition.

## 5. Lab Validation

The detection was tested using:

```powershell
powershell.exe -NoProfile -Command "whoami; ipconfig"
```

The search was saved in Splunk with a five-minute schedule and a trigger condition requiring more than zero results.

The matching activity and alert were then checked in Splunk.

**Validation outcome:** The alert was observed during the lab test.

This validates the configured detection against the test activity; it does not demonstrate that every malicious PowerShell technique will be detected.

## 6. Investigation Outcome

Use one of the following dispositions after reviewing the available evidence:

- **Benign:** The activity is explained by authorized or expected behavior.
- **Suspicious — further investigation required:** The activity is unusual, but the evidence is inconclusive.
- **Escalated:** Supporting evidence justifies incident-response investigation.
- **False positive:** The alert was generated by activity that does not represent the intended threat.

Do not assign a final disposition without supporting evidence.

## 7. Lessons Learned

- Detection rules require validation with controlled test activity.
- A matching keyword does not establish malicious intent.
- Process context and surrounding events improve investigation quality.
- Alerting is only one stage of the SOC workflow.
- Documenting evidence and reasoning makes investigations reproducible.

## Scope and Limitations

This project demonstrates basic SIEM detection, alert configuration, and investigation methodology in a controlled lab. It is an educational exercise and does not claim comprehensive attack detection or production incident-response capability.
